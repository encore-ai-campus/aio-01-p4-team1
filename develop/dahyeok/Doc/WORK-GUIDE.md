# 다혁님 · 맡은 일과 협의 순서

> 상태: 팀장이 준비한 작업 지침. 아래 담당·절차를 기준으로 진행한다. 팀장이 배포한 기본안을 적용한다. 아래 상대 표는 변경이 필요할 때의 연락 기준이며, 실제 구현·시험은 아직 끝난 것이 아니다.

## 1. 내 작업 범위

workflows/oke-support.json·본체 전용 보조 파일/로컬 시험 입력·Doc. 검색·이관 JSON과 다른 폴더는 수정하지 않는다.

**수정·생성·삭제·이동은 `develop/dahyeok/` 안에서만 한다.** 루트 docs·README·AGENTS·.env.example·다른 이름 폴더는 읽기만 한다. 상대의 코드를 복사해서 중복 구현하지 않는다. DB 접속·API 호출은 파일 수정 권한과 별개이며 합의한 계약과 자격증명으로 수행한다.

## 2. 기본안을 읽고 개발 시작

1. 저장소 루트 docs/TOPIC.md·API-CONTRACT.md·BASELINE-v0.md·DATA-AND-DB.md에서 기존 결정과 팀장 배포 기본안을 확인한다.
2. 자기 TODO·SPEC·IMP-PLAN에 기준을 적용하고 지정 단계부터 구현한다. 기준대로 개발할 때는 상대의 별도 재승인을 기다리지 않는다.
3. 아래 상대 표는 **변경이 필요할 때** 사용할 연락망이다. 모든 항목을 미리 재협의하는 선행 과제가 아니다.
4. 실제 서비스가 아직 없으면 같은 계약의 Mock으로 진행한다. 실제 연결은 제공자 준비 뒤 검증한다.
5. 기본안을 바꾸려 할 때만 자기 HANDOFF로 변경 요청하고 오현님의 공통 기준 갱신 뒤 수정한다.

## 3. 변경할 때 누구와 무엇을 확인하나

| 연결 ID | 상대 | 내가 먼저 보낼 것 | 상대에게 받을 것 | 맞춰야 하는 시점 |
| --- | --- | --- | --- | --- |
| C02 | 지혜님 | 본체 웹훅 입력/출력·인증·route·오류·로컬 실행 정보를 제공한다. | 웹 문의가 전달할 신원·attempt/context·서버 시간 제한 | 웹 API와 본체 연결 전 |
| C03 | 유빈님 | 검색에 필요한 query·type·권한 문맥·티켓 문맥안을 보낸다. | search 근거 목록 형식·빈 목록/실패 구분·시간 제한·인증 | 검색 호출 구현 전 |
| C04 | 원민님 | 이관의 request_id·requester·요약·유형·긴급도·사유를 보낸다. | handoff ticket·duplicate·실패 사유·부분 실패 응답 | 이관 호출 구현 전 |
| C08 | 원민님 | Agent·분기·루프·차단·권한·중복 기대와 관련 사례를 제공한다. | 공통/팀 테스트 기대와 실제 실패 보고서 | 각 기능 연결 전후 |

협의할 때 “완성되면 알려주세요”로 끝내지 않는다. **입력 JSON·성공 JSON·실패 JSON/HTTP 상태·권한·시간 제한·버전·확인 방법**을 함께 맞춘다.
DB 연결은 테이블/컬럼·벡터 차원·거리·권한·마이그레이션 순서, 실행 환경은 서비스명·포트·환경변수 이름·실행 위치까지 적는다.
환경변수 실제 값·비밀번호·토큰은 기록하지 않는다. 협의 기록과 공통 반영은 [팀 협업 절차](../../../docs/COORDINATION.md)를 따른다.

## 4. 개발 순서와 끝내는 기준

| 단계 | 할 일 | 끝내는 기준 |
| --- | --- | --- |
| P0 | 공통 계약을 읽고 C02/C03/C04를 맞춘다. Webhook→입력/차단 검사→임시 응답 골격을 만든다. | 입력 오류·차단 경로를 직접 확인하고 JSON check 통과 |
| P1-1 | 분류 Agent와 search·접수 조회·답변 Agent를 연결한다. | 권한 있는 근거가 있는 정상 답변 |
| P1-2 | 검증 Agent·보완 질문·검색 없음·긴급·handoff를 연결한다. | attempt 한도·검증 실패·근거 없음·긴급 이관 |
| P1-3 | 하위 지연·LLM 중단·보안·중복·복합 문의를 안정성 담당과 검증한다. | 전체 공통 시험 실제 결과·실패 수습 기록 |

단계 크기는 혼자 설명하고 확인할 수 있는 PR 한 건으로 쪼갠다. 위 표는 개인 개발의 진행 순서이며, 각자 모든 기능을 완성한 뒤 한 번에 연결하지 않는다.
팀장 배포 기준을 적용해 구현하고 제공자의 실제 응답이 준비되면 연결 PR을 만든다.
P1에는 권한·개인정보·오류·중복·복구 등 필수 안정성도 포함한다. P2는 P1 검증 뒤 팀장이 범위를 정한다.

## 5. 내가 내야 할 결과물

본체 JSON·노드/Agent 역할 카드·분기/병렬/루프 설명·연결선별 실제 페이로드·개별 check 결과. 설계서 반영 자료는 develop/dahyeok/Doc/SUBMISSION-NOTES.md로 제공한다.

루트 제출 문서는 직접 수정하지 않고 자기 Doc/SUBMISSION-NOTES.md에 **반영할 문서·절 / 실제 설계 / 측정·보고서 경로 / 남은 문제**를 정리해 오현님에게 넘긴다.
코드·JSON은 담당자가 구현한 뒤 생성한다. 확인하지 않은 노드·수치·PASS를 채우지 않는다.
기능을 완성하면 자기 README에 설치·실행·확인 명령과 상대 서비스가 필요한 조건을 적는다.

## 6. 작업 한 건을 진행하는 방법

1. 최신 main 기준으로 `feat/dahyeok-작업명` 브랜치를 만든다. 미커밋 작업이 있으면 먼저 안전하게 정리한다.
2. 자기 SPEC 요구 ID와 이번 단계·수정 파일·통과 기준을 정한다.
3. 코딩 에이전트에는 자기 폴더와 지정 단계만 허용한다. 공통/상대 파일을 고치려 하면 중단하고 변경 요청을 남긴다.
4. 자신의 기능을 실행해 확인한다. n8n check 뒤 push·test는 사람이 수행하며 개인 로컬 n8n에서 자기 워크플로우만 올린다. 팀 VM 배포는 오현님만 한다.
5. `git diff --name-only`, `git diff --cached --name-only`로 수정/스테이징 경로를 확인한다. 일반 담당자는 자기 폴더 밖 파일을 PR에 넣지 않는다.
6. PR에 요구 ID·수정 경로·계약 ID/기준 버전·실제 확인 결과·Mock 사용·남은 문제를 적는다. 리드가 검토·병합하고 통합 시각을 알린다.

폴더 규칙은 Git 작업 절차와 에이전트 지침이다. OS 파일 접근을 기술적으로 차단한 상태는 아니므로 PR에서도 경로를 확인한다.

## 7. 에이전트에 줄 작업 요청

```text
현재 작업 폴더는 develop/dahyeok/이고 내 역할은 문의 처리 자동화이야.
루트 AGENTS.md와 docs/TOPIC.md·API-CONTRACT.md·COORDINATION.md,
이 폴더 AGENTS.md·README.md·Doc/WORK-GUIDE.md·SPEC.md·IMP-PLAN.md·HANDOFF.md를 읽어.
내가 지정한 요구 ID와 단계만 진행해. develop/dahyeok/ 안에서만 파일을 수정·생성·삭제해.
상대/공통 파일 변경이 필요하면 내 Doc/HANDOFF.md에 요청안만 적고 상대 파일은 고치지 마.
이번 수정 파일·입출력·통과 기준을 먼저 정리하고, 완료 후 실제 검사와 미실행을 구분해 보고해.
```

오현님의 공통 파일 정비는 리드 작업으로 허용되며, 해당 공통 경로를 작업 요청에 명시한다.
