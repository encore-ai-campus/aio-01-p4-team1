# 80일차 · 점검과 발표 준비

아침 주제·역할 소개는 [README](README.md)를 그대로 열어 발표한다. 이 문서는 오후 점검·발표의 준비용이다.

**5교시는 설계 1차 점검, 8교시는 산출물 발표 ①이며 각각 팀별 10분이다.** 발표 때 GitHub 문서와 팀 VM을 연다. 아래는 우리 팀용 진행안이며 실제 결과는 당일 확인 후 공통 문서에서 보여 준다.

## 지금 바로 준비할 설명

- 주제·문제·사용자: [TOPIC의 1분 발표문](../../../docs/TOPIC.md#6-주제-설명--1분-발표문)을 사용한다.
- 팀 명단·역할: [TEAM-CHARTER](../../../docs/TEAM-CHARTER.md)의 역할표를 보여 준다.
- 서비스 그림: [ARCHITECTURE](../../../docs/ARCHITECTURE.md)와 [예상 화면](../../../docs/PREVIEW.md)을 연다.
- 본체·RAG 계획: [WORKFLOW-DESIGN](../../../docs/WORKFLOW-DESIGN.md) 1~4절과 [RAG-ARCHITECTURE](../../../docs/RAG-ARCHITECTURE.md) 1~2절을 사용한다.

화면·그림은 구현 전 설계다. 담당자 브랜치의 Mock·로컬 결과는 준비 현황으로 말하고, 실제 VM 통과 수·색인 수처럼 발표하지 않는다.

## 5교시 · 1차 점검에 보여 줄 것

1. 오케퐁 직원 6명의 사내 IT 문의를 처리하며, 근거가 없거나 실제 조치가 필요하면 IT팀에 넘긴다는 범위를 설명한다.
2. 다혁님과 대조한 설계 1~4절에서 수신→입력/권한 검사→분류→검색/답변/검증→이관의 계획을 보여 준다.
3. triage·writer·verifier 역할과 분기·병렬·보완 루프의 목적·한도를 설명한다. 실제 노드가 있는 부분과 계획만 있는 부분을 구분한다.
4. 공통 요청·응답은 [API](../../../docs/API-CONTRACT.md)와 [평가 기준](../../../docs/EVALUATION-GUIDE.md)대로 유지한다고 설명한다.
5. 원민님 팀 사례 초안의 질문·조건·기대를 보여 준다. 원격 초안이 공식 도구 형식으로 확인되지 않았다면 그 상태를 설명한다.
6. 입력 오류·주입 차단이 실제로 실행됐으면 보고서를 연다. 아직 로컬 Code/Mock뿐이면 VM 시험 전이라고 말한다.

이 자리에서 받을 질문: 범위가 3일에 맞는지, 흐름·분기·팀 사례의 기대가 공통 기준과 맞는지, 아직 해결되지 않은 연결을 어떻게 조정할지. 강사 답변은 실제 받은 뒤 기록한다.

## 8교시 · 10분 발표 진행안

| 시간 | 설명 | 화면·받을 자료 |
| --- | --- | --- |
| 0~2분 | 주제·해결할 문제·6명 역할·오늘 목표 | TOPIC·헌장. 지금 준비 가능 |
| 2~5분 | 본체 흐름·Agent 3역할·분기/병렬/루프·현재 구현 범위 | 다혁님 설계 1~4절 대조 자료·JSON·실제/Mock 구분 |
| 5~7분 | 원본·청킹·임베딩/pgvector 계획과 실제 색인 현황 | 유빈님 RAG 1~2절·문서/청크 수·길이 분포. 미측정 칸은 미측정 |
| 7~9분 | VM에서 게시한 워크플로우·입력/차단 동작·시험 결과 | 오현님 배포 커밋·원민님 실제 보고서. VM 동작은 해당 환경에서만 확인 |
| 9~10분 | 실패·막힘·필요한 도움·81일차 첫 작업 | DAY80 실제 기록과 담당·다음 확인 시점 |

발표 순서·분량은 우리 팀 제안이다. 강사가 당일 안내한 방식이 있으면 조정한다. 첫날 미완성 기능은 계획·진행 중으로 소개하고, 실행하지 않은 시연을 성공 장면처럼 대체하지 않는다.

이 표는 준비 단계의 수신 목록이다. 실제 수치·승인·피드백의 기록 원본은 공통 문서이며, 바뀔 때마다 이 파일에 별도 결과서를 만들지 않는다.

- [ ] 발표 피드백과 내일 계획은 [공식 DAY80](../../../daily/DAY80.md)에 기록한다.
