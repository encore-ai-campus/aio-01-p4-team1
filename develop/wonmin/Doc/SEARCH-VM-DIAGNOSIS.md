# oke-search VM 원인 분석 · 2026-11-06

현재 장애는 재현되지 않았다. 실제 팀 VM 터미널에서 실행 중인 컨테이너를 사용해 검색 함수와 n8n 운영 웹훅을 각각 확인했다. Mock 결과가 아니다.

| 확인 경로 | 실제 결과 |
| --- | --- |
| 검색 함수 → OpenAI 임베딩 → PostgreSQL 벡터 검색 | 임베딩 200, 검색 응답 200, 근거 3건, 1.404초 |
| 백엔드 컨테이너 → n8n 운영 `/webhook/oke-search` → 검색 서비스 | HTTP 200, ok=true, reason=null, 근거 3건, 2.227초 |
| 검색 서비스용 키로 n8n 운영 웹훅 호출 | HTTP 403, 0.033초. 실제 백엔드 키로 호출하면 위와 같이 성공 |

검색 DB에는 문서 8개·청크 33개가 있고 text-embedding-3-large/3072차원이 일치했다. 운영 HTTP 노드의 URL 환경변수는 설정되어 있으며 Header Auth Credential도 연결되어 있다. API 키나 비밀번호는 기록하지 않았다.

## 화면이 동작하지 않는 것처럼 보이는 조건

- 편집기에서 관찰한 No input data / No output data는 해당 수동 실행의 입력·출력이 없는 상태다. 운영 웹훅 호출의 실패 증거는 아니다.
- URL 미리보기의 `[ERROR: not accessible via UI, please run node]`를 환경변수 미설정으로 판단하면 안 된다. VM에서 URL이 설정된 것과 운영 호출 성공을 별도로 확인했다.
- Search 설정은 성공·오류 실행 저장 모두 none, 수동 실행 저장 false였다. 실행 목록 부재만으로 미실행이라고 판단할 수 없다.
- Execute workflow의 Test URL 대기와 운영 `/webhook/` 호출은 다르다. 수동 시험에는 해당 워크플로우가 표시하는 Test URL로 올바른 인증과 C03 본문을 보내야 한다. 브라우저로 workflow 편집기 URL을 여는 것만으로 검색이 실행되지는 않는다.
- 검색 서비스용 키와 n8n 수신 웹훅용 키는 이번 관측에서 호환되지 않았다. 호출 구간에 맞는 Credential을 사용해야 한다. 실제 백엔드 키를 사용한 운영 호출은 성공했다.

## 남은 확인과 담당

실제 실패한 요청 시각·HTTP 상태·응답 reason이 확보되지 않아 간헐 실패 원인은 확정할 수 없다. 검색 제공자 timeout 3초, n8n HTTP timeout 4초는 코드·설정에서 확인되는 제약이며 이번 성공 측정으로 지연 장애를 배제할 수 없다. 다음 실패 시 유빈님과 비밀을 제거한 실패 응답을 같은 시각에 대조하고, 필요하면 팀장 관리 아래 제한된 진단 기록을 확보한다. 본 조사에서는 저장 설정·Credential·워크플로우·서비스를 변경하거나 재배포하지 않았다.

관측값은 `../runs/vm-search-observed-20261106.json`에 기록했다. 터미널 화면을 읽어 전사한 값이며 자동 수집 raw JSON이라고 표기하지 않는다. 반복·동시 부하·간헐 장애 재현 시험은 수행하지 않았다.
