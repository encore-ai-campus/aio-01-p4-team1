## 목적과 사용자

직원은 자동 답변이 어려울 때 실제 접수 여부와 실패 안내를 알아야 한다. IT팀은 중복 티켓 없이 긴급 문의·저장 실패를 확인해야 한다. 팀장은 보고서에서 어떤 조건이 실패했고 수정 뒤 같은 조건에서 복구됐는지 확인할 수 있어야 한다.

단계 분류: **P0 기반 → P1 필수 MVP → P2 선택 고도화**.

## 적용할 기준과 변경 경계

C04/C05 입력·응답, 티켓 `key=request_id`, 신규 201·중복 200, `normal/high`, `POST /alerts` 선택 `event_key`, `POST /dlq`, X-Team-Key/X-Api-Key, practice/app 대상과 app 테이블은 이미 정해져 있다. 새 승인 없이 [SPEC 적용할 기준](SPEC.md#적용할-기준)으로 진행한다.

공통에 빠진 retry 수치·부분실패 ok 의미·관측 조회 세부 경계는 HANDOFF WM-01~WM-04의 제안이다. 확정 전에는 해당 경계를 Mock으로 시험하고 공통 기준 확정 또는 서비스 준비가 필요한 항목을 미판정으로 남긴다. 나머지 문서·정상/중복 경로 개발을 멈추지 않는다.

## P2 선택 고도화

- 자동 DLQ replay, 회로 차단, 알림 묶음 전송 고도화, 장시간 부하 시험은 필수 증거 뒤에 진행한다. 수동 복구·동일 키 재시험과 동시성 확인은 P1 필수다.

## 범위와 측정 원칙

- 텔레그램·새 화면·새 DB 스키마 구현·검색/문의 본체 복제는 본인 필수 범위에 넣지 않는다.
- 수치 목표는 실측 없이 정하지 않는다. 검색 품질과 시간은 SPEC REL-06의 측정 절차로 근거를 만든다.

## 의존성과 전달

다혁님은 동일 support의 handoff 호출·최종 응답 매핑과 부모 오류 설정을, 지혜님은 저장 API·DB 거래·권한·관측을, 유빈님은 검색 근거·점수 기록을 제공한다. 서비스가 없으면 계약 Mock을 사용한다. 문서 검토·제안 승인·통합 일시·실행 결과는 아직 없다. 검토자는 C04 다혁님, C05 지혜님, 공통 반영·취합 오현님이다.
