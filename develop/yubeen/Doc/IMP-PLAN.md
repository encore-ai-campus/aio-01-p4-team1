## 작업 위치와 단계 운영

모든 명령의 작업 디렉터리는 저장소 루트 기준 `develop/yubeen`으로 지정한다. 아래 `python3 tools/...`와 설정 이름·옵션은 **구현 예정 인터페이스**다. 도구를 구현하고 도움말·입출력을 확인하기 전에는 실행 가능한 기존 명령으로 간주하지 않는다. 환경변수 이름은 공통 계약의 `DATA_API_URL`, `DATA_API_KEY`, `DATABASE_URL`, `N8N_WEBHOOK_URL`, `N8N_WEBHOOK_KEY`를 적용하고 실제 값은 기록하지 않는다. OpenAI 키는 n8n Credential로 관리한다.

DB·원본·n8n이 준비되지 않은 단계는 같은 계약의 Mock으로 확인한다. Mock 결과와 실제 연결 결과를 따로 기록한다. 기존 마이그레이션이 없으면 지혜님 산출물이 준비될 때 DB 연결을 확인하며, 자기 폴더에 대체 마이그레이션을 만들지 않는다. 정책 제안 검토를 기다리는 동안 전처리·정답표·계약 Mock은 계속한다.

## P0-1 · 첫 작업: 원본·권한·절 대장

- 연결 SPEC: RAG-01·02.
- **생성 예정**: `tools/rag_prepare.py`, `Doc/SOURCE-MANIFEST.md`, `Doc/INDEX-RESULT.md`의 원본 확인 절. 도구는 원본 수집·해시·절/청크 분석을 위한 개인 도구이며 서버/DB를 만들지 않는다.
- 입력: 공통 data-api의 문서 목록과 개별 본문. 도구에 먼저 비밀값 없는 목록/본문 Mock을 주고 정상·빈 문서·중복 키·권한 누락을 확인한다.
- 작업: `/docs`의 실제 응답 구조와 각 `name`·제목·원문 경로·조회시각·LF 정규화 해시·절 제목/본문 길이·권한 값·권한 근거를 기록한다. 규정 8종과 관리자 문서 제공 여부를 대조한다. 관리자 원문·비밀값을 일반 결과 문서에 복사하지 않고 식별자·권한·해시로 추적한다.
- 권한 확인이 불가능한 문서는 대장에 미확인/색인 거절로 적는다. 제목이나 파일명만 보고 권한을 추정하지 않는다. 권한 출처 보완은 H-Y02에 남기되 권한 없는 문서도 목록/길이 조사까지는 진행한다.
- 확인 예정 명령: `python3 tools/rag_prepare.py inventory --source api --output Doc/SOURCE-MANIFEST.md`. 실제 도구 구현 시 이 옵션과 환경변수 입력을 함께 제공한다. API 미준비 시 같은 응답 모양의 Mock 실행임을 결과에 표시한다.
- 완료 기준: 각 원본에 식별자·절·해시·권한/근거 또는 거절 사유가 있고, 누락 문서를 성공 건수에 넣지 않는다. 이 단계 완료는 전체 색인 완료가 아니다.
- 다음에 넘길 결과: P0-2에는 고정할 원본/권한 목록, 지혜님에는 기존 DB 컬럼에 넣을 값의 표본, 원민님/오현님에는 자료 누락과 권한 미확인 사실. 실제 전송 여부는 별도 기록한다.

## P0-2 · 정답표와 청킹 비교 준비

- 연결 SPEC: RAG-01·02·04·07.
- **생성 예정/수정 예정**: `tools/rag_prepare.py`, `Doc/CHUNK-COMPARISON.md`, `Doc/SEARCH-EVAL.md`, `cases/rag-search.json`, `requests/search-all.json`, `requests/search-it.json`. 요청/사례 파일에는 키·원문 관리자 본문·연락처를 넣지 않는다.
- 작업: SPEC Q01~Q16의 실제 문서·정확한 절·필수 답 문구를 원문과 대조해 검색 전에 고정한다. 관리자 문서 미제공 사례는 미실행으로 표시한다. 빈 후보·동점·입력 불량·DB/임베딩 오류 기능 사례는 품질 질문과 분리한다.
- 기본은 `##` 절 단위 overlap=0, 비교는 본문 300자 overlap=0이다. 서문·절 없는 문서·빈 절·목록/표·코드 블록 내부 제목·절 경계를 걸친 비교청크를 확인한다. 두 방식의 문서/절/원문 범위와 content 표본을 대조한다.
- 확인 예정 명령: `python3 tools/rag_prepare.py compare-chunks --source api --baseline section --candidate 300 --output Doc/CHUNK-COMPARISON.md`. 두 방식을 같은 원본 스냅샷으로 계산하는 옵션으로 구현한다. 이 명령은 임베딩/DB 저장 없이 청크를 비교한다.
- 완료 기준: 같은 원본 해시·권한·접두어 규칙으로 두 방식의 청크 수와 본문/접두어 포함 길이 최소·중앙·최대가 계산되고, 원문 손실·절 추적 실패를 설명할 수 있다. 실제 실행 전 통계값은 비워 두거나 미측정으로 쓴다. 정답표 수정 이력은 실행 전/후를 구분한다.
- 다음에 넘길 결과: P1-1에는 청크 매핑·기본 설정, 다혁님에게는 C03 정상/빈 결과/장애 예시, 원민님에게는 권한 쌍과 고정 기대. 공통 사례 기대는 수정하지 않는다.

## P1-1 · 문서 단위 색인·임베딩·저장

- 연결 SPEC: RAG-01·02·05.
- **생성 예정**: `workflows/oke-index.json`, `config/rag-settings.json`, `tools/rag_verify.py`. **수정 예정**: `Doc/INDEX-RESULT.md`.
- 입력: 확인된 문서·권한, P0-2 기본청킹, 지혜님이 준비한 기존 두 테이블·DB 연결. 설정에는 모델·3072차원·cosine·top_k=3·청킹 버전을 명시한다. 임계값은 숫자 기본값을 꾸미지 않고 미확정으로 구분한다. 전처리 도구와 워크플로우 청크의 content/hash가 같은지 대조한다.
- 작업 순서: 원본/권한 검증 → 변경 감지 → 청킹 → 모든 임베딩의 모델/차원/유한 수치 검증 → 한 문서의 저장 트랜잭션 → 문서별 성공/건너뜀/실패 요약. 임베딩을 받기 전에 이전 청크를 지우지 않는다.
- DB 확인: 지혜님 마이그레이션이 `rag.documents`·`rag.chunks`, FK·고유키·vector(3072)를 제공하는지 읽기 확인한다. 실제 저장 경로가 한 연결의 트랜잭션인지 확인한다. 필요한 함수/구조 추가만 C06으로 요청하고 DDL은 지혜님이 작성한다.
- 확인 예정 명령: `python3 tools/rag_verify.py index --scenario initial-and-repeat --output Doc/INDEX-RESULT.md`. 구현 시 이 명령은 문서별 건수·해시·차원·권한을 비교하고 기존 보고서의 다른 절을 보존하도록 만든다. n8n 색인 호출/실행은 아래 사람 수행 구분을 따른다.
- 완료 기준: 동일 입력 두 번의 문서/청크 수·해시 불변, 벡터 3072차원·동일 모델, FK/고유키 일치, 미확인 권한 거절, 부분 임베딩 실패의 이전 성공본 보존. 외부 미준비로 Mock만 확인했으면 실제 색인 완료가 아니다.
- 다음에 넘길 결과: P1-2에는 실제 DB 매핑과 성공 색인 식별값, 지혜님에는 구조/접속 불일치 재현, 원민님에는 중복·실패 사례와 실제 결과 경로.

## P1-2 · 권한 SQL과 search 계약

- 연결 SPEC: RAG-02·03.
- **생성 예정**: `workflows/oke-search.json`. **수정 예정**: `tools/rag_verify.py`, `cases/rag-search.json`, `Doc/SEARCH-EVAL.md`의 계약 검증 절.
- 작업 순서: X-Team-Key 검증 → 입력/권한 목록 검증 → query 임베딩 → documents 권한으로 제한한 chunks 후보 → 같은 모델의 cosine 정확거리 정렬 → 최대 3개 → score와 evidence 매핑 → HTTP 응답.
- 분리할 경로: 정상 200/reason=null, 빈 후보 200/no_evidence, 임베딩/DB/시간 초과 장애 503/search_unavailable. `type`은 분류 문맥으로 받고 초기 추가 필터로 쓰지 않는다. H-Y01의 미확정 오류 세부안을 확정 계약처럼 배포하지 않는다.
- 확인 예정 명령: `python3 tools/rag_verify.py search --cases cases/rag-search.json --output Doc/SEARCH-EVAL.md`. 현재 도구/사례/서비스가 없으므로 미실행이다. 구현 시 요청별 HTTP·스키마·정렬·허용 doc·0/1/3개·장애를 검사하고 Mock/실제 모드를 결과에 명시한다.
- 확인 방법: 일반 직원의 허용 집합에서 top3를 구한 결과와 비교한다. 제한 문서가 전역 top3를 차지하는 별도 시험에서도 허용 문서를 제대로 찾는지 확인한다. 실제 SQL의 바인딩·권한 조건·거리 연산자·제한 순서·실행계획을 점검한다. 검색 후 필터로 대체하지 않는다.
- 완료 기준: SPEC 응답 필드·HTTP가 맞고, 일반 직원의 후보/evidence/본체 LLM 입력에서 it 본문 노출 0건이며 IT 권한 양성 검색도 확인된다. 본체가 아직 없으면 LLM 입력 경로는 미확인으로 남긴다.
- 다음에 넘길 결과: 다혁님에게 실제 C03 요청/응답과 실행 버전, 원민님에게 SQL 권한 사례·장애 재현·관측 위치. 받는 담당자의 소스는 고치지 않는다.

## P1-3 · 같은 질문으로 검색 품질·시간 측정

- 연결 SPEC: RAG-04·07.
- **수정 예정**: `tools/rag_verify.py`, `Doc/CHUNK-COMPARISON.md`, `Doc/SEARCH-EVAL.md`, `config/rag-settings.json`의 검토 후 확정된 값만.
- 사전 조건: P0-2 정답표 고정, 실제 검색 준비, 운영 데이터와 분리한 DB. 두 청킹 색인을 동시에 공통 테이블에 섞지 않는다. 비교 후 기본 색인을 복원하고 설정/해시를 다시 확인한다.
- 절차: 절 단위 색인 → 고정 질문별 3회 측정 → 격리 DB에 300자 색인 → 같은 질문·권한·모델·3072차원·cosine 정확검색·top_k=3으로 3회 측정. 한 번에 청킹만 바꾼다. 토큰·청크 수·시간을 각각 기록한다.
- 확인 예정 명령: `python3 tools/rag_verify.py evaluate --cases cases/rag-search.json --repeats 3 --output Doc/SEARCH-EVAL.md`. 사람의 색인/시험 실행 근거를 입력받아 집계하는 방식과 직접 조회하는 방식을 구현 시 구별한다.
- 완료 기준: 질문별 순위·절·답 근거·점수·권한·HTTP·임베딩/DB/search 시간, 분자/분모가 있는 hit@3·절 hit@3·근거 포함률, 답 없음 오답·누출 수, N·중앙·p95·최대가 실제 자료에서 계산된다. 검색 실패도 별도 집계한다. 품질/시간 목표가 미확정이면 목표 통과라고 쓰지 않는다.
- 임계값 검토: 답 있음·없음·유사하지만 답 없음의 분포와 보류 질문 결과를 제시한다. 본체의 답 검증과 함께 확인하고 H-Y04에 제안한다. 측정한 값만으로 공통 자동 답변 정책을 임의 확정하지 않는다.
- 다음에 넘길 결과: 다혁님에게 점수 의미·임계값 후보·실제 시간, 원민님에게 실패 질문/경계 사례, 오현님에게 두 방식 비교와 변경 제안 여부.

## P1-4 · 갱신·중단 복구와 재시작 유지

- 연결 SPEC: RAG-05·06.
- **생성 예정**: `Doc/RECOVERY-RESULT.md`. **수정 예정**: `tools/rag_verify.py`, `Doc/INDEX-RESULT.md`.
- 격리 원본의 한 문서를 변경하고, 청크가 늘어나는 경우와 줄어드는 경우를 각각 갱신한다. 다른 문서의 해시·건수 불변과 이전 잔여 청크 제거를 확인한다. 임베딩 실패와 저장 도중 실패를 각각 일으킨 뒤 롤백·재실행을 확인한다.
- 기준 건수·해시·권한·고정 질문 결과 기록 → 관리 담당자가 n8n 재시작 → 재색인 없이 비교 → 같은 named volume으로 PostgreSQL 재시작 → 재색인 없이 비교 순서로 수행한다. 유빈님이 공통 Compose를 수정하거나 운영 볼륨을 삭제하지 않는다.
- 지혜님이 준비한 새 DB·마이그레이션에서 같은 원본/설정으로 재색인한다. doc_key·chunk_no·content_hash, 누락/중복·권한 검색을 비교하고 복구 전체 시간·실제 토큰·실패/재시도를 잰다. 백업 복원 시험은 지혜님이 별도 환경에 복원한 뒤 같은 비교를 수행한다.
- 확인 예정 명령: `python3 tools/rag_verify.py recovery --phase before --output Doc/RECOVERY-RESULT.md`, 관리 담당자의 재시작 후 `python3 tools/rag_verify.py recovery --phase after --output Doc/RECOVERY-RESULT.md`. 구현 시 before 자료를 덮어쓰지 않고 환경/실행 ID로 전후를 연결한다.
- 완료 기준: 같은 볼륨 재시작에서 데이터 유지, 중단 후 중복 없는 재처리, 새 DB 재생성의 건수·해시·권한 검증과 실제 시간이 기록된다. 백업 미제공/재시작 미수행은 미실행이다. 원문 삭제·권한 변경·동시 갱신·백업 운영정책은 H-Y03 미반영 상태를 명시한다.
- 다음에 넘길 결과: 지혜님에게 저장/복구 검증 차이, 원민님에게 재현과 후처리 상태, 오현님에게 실제 복구 기록과 운영정책 미결 사항.

## n8n 확인·사람 수행의 구분

구현 후 JSON 정적 확인은 80일차 평가 키트 `flow.py check`를 사용한다. 키트의 실제 위치·버전을 먼저 확인하고 기록한다. 아래는 **경로 치환이 필요한 예정 명령**이며 현재 실행하지 않았다. 작업 디렉터리는 이 문서 첫 절의 개인 폴더다.

```text
uv run <80일차_키트_경로>/tools/flow.py check workflows/oke-index.json
uv run <80일차_키트_경로>/tools/flow.py check workflows/oke-search.json
```

키트가 없으면 정적 검사도 미실행으로 적는다. 다른 날짜 키트로 확인한 결과를 80일차 검증 완료로 쓰지 않는다. **push·test·서비스 재시작·VM 배포는 사람이 관리하는 실제 실행 단계**로 구별한다.

## 실행 후 기록 양식

각 결과 파일에 `단계 / SPEC ID / 날짜·실행 ID / 실제 생성·수정 파일 / 원본·설정·환경 버전 / 작업 디렉터리·명령 또는 사람의 실행 근거 / Mock·실제 / 입력 / 기대 / 실제 HTTP·출력·종료 코드 / 완료·실패·미실행 / 증거 경로 / 남은 문제 / 다음 담당자에게 넘길 결과`를 적는다.
