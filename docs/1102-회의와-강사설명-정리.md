# 11월 2일 강사 설명·팀 회의 정리

> 작성: 2026-11-02. 전사문과 수업 자료를 대조한 정리입니다. 발언자가 식별되지 않는 문장은 특정 팀원의 의견으로 배정하지 않았습니다. 구현·시험 결과가 아닙니다.

## 1. 이번 회의의 결론

**사내 IT 헬프데스크를 선택하고, 제공 데이터를 활용해 실제 사용자가 쓸 수 있는 서비스와 외부 연동에 집중한다.** 새 도메인의 자료 조사에 시간을 쓰기보다 n8n·RAG·화면·백엔드가 연결되는 경험을 얻으려는 방향입니다.

| 구분 | 확인한 내용 |
| --- | --- |
| 결정 | 1번 사내 IT 헬프데스크로 진행 |
| 진행 방향 | 기본 기능부터 만들고, 시간과 완성도를 보며 다음 단계로 확장 |
| 차별화 방향 | 자료를 새로 만드는 양보다 서비스의 실용성·연동 완성도에 집중 |
| 역할 방향이 명시된 부분 | “RAG는 유빈님이 하시고”라는 발언. 나머지 담당은 이번 전사문만으로 확정할 수 없음 |
| 미결정 | 회사명·업종·규모, B/C 조합, 외부 서비스, 기술 스택, 세부 역할 |
| 검토만 한 부분 | Supervisor·병렬·Handoff 등 오케스트레이션 방식. 특정 패턴으로 최종 합의한 것은 아님 |

회의 근거: “1번으로 진행하되”, “실용성 면에서”, “사용자가 사용할 수 있는 서비스를 만들어서”, “원스텝 투 스텝”, “카테고리는 아직”이라는 대목. 전사 오류가 있어 문장 전체를 확정 발언처럼 재구성하지 않았습니다.

## 2. 팀이 실제로 걱정하는 것

| 고민 | 회의에서 드러난 맥락 | 기획에 반영할 방법 |
| --- | --- | --- |
| 도메인을 모르는데 무엇을 해결하는가 | 다른 후보의 문의·문서·해결 범위가 낯섦 | 제공 규정으로 반복 문의를 안내하고, 해결 불가능한 요청을 IT팀에 정확히 전달하는 문제로 제한 |
| 개발보다 통합에 시간이 들 수 있음 | 환경 설정·Git 병합·서로 다른 데이터 형식 우려 | 화면·API·n8n 사이의 요청·응답을 먼저 합의하고 작은 흐름부터 연결 |
| 역할표에 프론트·백엔드·DB가 안 보임 | 워크플로우 중심 역할만으로 전체 서비스 담당이 불분명 | C형 선택 시 웹 연결·API·DB 담당을 명시. 디자인과 API 연결을 구분 |
| 무엇부터 만들고 어디까지 확장할지 불명확 | 뒤늦은 기능 추가로 큰 수정을 피하고 싶음 | A 핵심 → C 최소 화면 → 외부 알림 1개로 단계화. 단계별 중단 기준 마련 |
| 회사 설정과 제공 데이터가 맞을까 | 온라인 유통사·학원·50~100명 규모 등이 언급됨 | 회사 설정은 설명용으로 최소화. 제공 직원·부서·티켓의 의미를 바꾸지 않음 |
| 어떤 오케스트레이션이 적절한가 | 중앙 조정·병렬·위임을 비교 | 결정 규칙을 n8n에 두고 분류·작성·검증을 분리하는 구조부터 시작 |

텔레그램·노션·디스코드·Jira 등은 **연동 후보**입니다. 여러 서비스를 모두 구현하기로 결정한 회의가 아닙니다. 가산점도 실제 구현·시연과 평가에 달려 있으며 연동 개수만으로 보장되지 않습니다.

## 3. HTML과 PDF의 차이

두 파일은 같은 38장짜리 아키텍처 슬라이드 자료입니다. HTML은 슬라이드 이미지를 담은 브라우저 발표용이고, PDF는 텍스트를 추출·검색할 수 있어 이번 분석은 PDF를 기준으로 했습니다. 대응 슬라이드의 내용·배치도 표본 대조했습니다.

| 강사 자료의 핵심 | 우리 프로젝트에 적용 |
| --- | --- |
| 입구 → n8n 판단 → 지식 검색·티켓·알림 (4~12쪽) | 화면이 직접 AI와 업무 처리를 모두 수행하지 않음 |
| A로 먼저 확인한 후 B/C 확장 (13~19쪽 및 설명) | 기존 A 우선안은 유지하되, 최종 목표는 서비스 화면을 포함하는 안으로 조율 |
| C는 직원·관리자 화면과 FastAPI·DB (18~19쪽) | 질문하기·내 문의·관리자 티켓 3개 화면으로 제한 가능 |
| 직원 선택으로 시작 가능 (19쪽) | 가상 직원 6명으로 시연. 실제 로그인·SSO를 구현했다고 표현하지 않음 |
| 필수 산출물은 설계서 2종·실행 결과서 (22~25쪽) | 화면 제작과 별개로 설계·검색 근거·실제 시험 기록을 남김 |
| 6명 역할 예시: 리드·오케스트레이션·RAG·연동 안정성·어댑터·QA (28쪽) | C형의 어댑터에는 웹·API가 포함됨. 팀 사정에 맞게 업무를 재배분 |
| 팀장은 취합·계약·배포·진행 관리 (29쪽) | 모든 연결 코드를 팀장 한 명이 작성하는 구조를 피함 |

## 4. 기존 문서와 구두 설명이 다른 부분

| 항목 | 문서·슬라이드 | 이번 구두 설명 | 계획에서의 처리 |
| --- | --- | --- | --- |
| 응답 종류 | 다섯 가지 공통 route | 주제에 따라 더 적을 수도 있음 | 기본 주제인 우리 팀은 다섯 가지를 유지하는 안. 줄여서 얻는 이익이 작음 |
| 공통 시험 | 14개, 원본 판정 유지 | 진행 상황에 따라 일부 제외 가능. WF-10 제외 예시도 언급 | 원본 14개는 보존. 제외가 필요하면 대상·사유·평가 적용 범위를 강사와 확인하고 별도 기록 |
| 장애·권한 구현 깊이 | 상세한 처리와 시험 안내 | 3일 안에 모두 구현하기 어려울 수 있음 | 키 보호·본인 조회·문서 권한·마스킹은 기본 계획에 유지. 세부 장애 시험 범위는 승인 시 조율 |
| OpenAI 키 | 모든 팀이 강사 키 하나를 공유한다는 기존 안내 | 팀 내 사용할 키를 정해 VM에 설정하도록 정정 | 팀 사용 키·사용량 관리 담당 지정. 값 자체는 문서에 기록하지 않음 |
| 스택·문서 형식 | Next.js·FastAPI와 폴더·템플릿 예시 | Streamlit 등 대안 및 팀별 조정 허용 | 역할·기한에 맞춰 선택. 실제 구현과 문서가 일치하도록 관리 |

전사문 초반에는 공통 14개 통과를 강조하고 후반에는 범위 축소를 허용합니다. 따라서 **전부 선택 사항으로 바뀌었다거나, 예외 없이 전부 필수라고 단정하지 않습니다.** 채점에 쓸 범위를 주제 승인 때 확인합니다. 제외·미실행·실패를 통과로 계산하지 않습니다.

## 5. 기존 준비 자료와 연결

- 주제 비교·구체화 문서는 선정 과정 기록으로 보존합니다. 다른 후보를 합쳐 범위를 넓힐 필요는 없습니다.
- 제공 지식 문서 8종·FAQ 6종·직원 6명·기존 티켓 4건을 출발점으로 삼습니다. 현 로컬에는 `Last3Mon/80`이 없어 실제 키트 확인은 남아 있습니다.
- 기존 TOPIC의 **한빛커머스는 예시 회사명**입니다. 회의에서 회사가 확정된 것으로 쓰지 않습니다.
- 기존 역할안에는 C형 웹·API 담당이 부족했습니다. 새 역할안은 이 연결 책임을 드러내되 당사자 수락 전까지 제안으로 표시합니다.
- [구현 기획안](IMPLEMENTATION-PLAN.md)은 위 결론을 실행 단계로 옮긴 **추천안**입니다. [팀 헌장](TEAM-CHARTER.md)에서 역할 조율 상태를 관리합니다.
