# 협의·파일 소유권·연결 순서

> 팀 운영 기준. 기술 계약의 상세 JSON은 관련 담당자가 제안하고 검토한 뒤 오현이 공통 문서에 반영한다. 아래 절차를 작성한 상태이며 협의·배포·시험 완료를 뜻하지 않는다.

## 1. 파일은 소유자 한 사람이 수정한다

| 파일 영역 | 편집 담당 |
| --- | --- |
| hyun/ · 루트 README·AGENTS·.env.example·docs/·공통 계약·최종 제출 취합 | 오현 |
| sueon/ | 이수언 |
| jihye/ (마이그레이션·deploy 포함) | 박지혜 |
| dahyeok/ | 임다혁 |
| yubeen/ | 신유빈 |
| wonmin/ | 이원민 |

다른 폴더는 읽고 합의한 API/DB를 호출할 수 있지만 파일은 수정하지 않는다.
공통 설계서에 쓸 내용도 개인 Doc/SUBMISSION-NOTES.md에 제공하고 오현이 옮긴다.
DB 접근 권한은 별도로 설계한다. 유빈님은 검색·색인 데이터를 쓰지만 DDL·마이그레이션 파일은 지혜님이 관리한다.

이번처럼 팀장이 요청한 공통 준비 문서 정비는 전 역할 문서를 대상으로 할 수 있다.
개발 담당자의 일상 구현에서 공통 파일을 수정할 수 있다는 의미는 아니다.

## 2. 연결별 협의 책임

| ID | 연결 | 먼저 제안할 담당 | 함께 결정할 상대 | 합의 결과 |
| --- | --- | --- | --- | --- |
| C01 | 화면 ↔ 웹 API | 수언: 화면·필드 요구 → 지혜: API 명세안 | 수언·지혜 | 엔드포인트·성공/오류 JSON·세션·권한·화면 상태 |
| C02 | FastAPI ↔ support | 지혜: 신원/질문 전달·오류 처리안 | 지혜·다혁 | 교사 공통 계약 준수·인증·시간 제한·응답 매핑 |
| C03 | support ↔ search | 다혁: 검색 입력 요구 → 유빈: 검색 응답안 | 다혁·유빈 | query·검증된 권한 문맥·evidence·빈 결과/장애 구분 |
| C04 | support ↔ handoff | 다혁: 이관 입력 → 원민: 결과/실패 응답안 | 다혁·원민 | request_id·긴급도·사유·ticket·중복·부분 실패 |
| C05 | handoff ↔ 저장 API | 원민: 저장/관측 요구 → 지혜: 호환 API 명세안 | 원민·지혜 | /tickets·/alerts·내부 인증·조회·멱등·실패 |
| C06 | RAG ↔ PostgreSQL+pgvector | 유빈: 차원/청크/검색 요구 → 지혜: DB 변경안 | 유빈·지혜 | 확장·테이블·메타데이터·필터·차원·거리·인덱스·접속 권한 |
| C07 | 모든 서비스 ↔ 배포 | 각 담당: 실행 정보 → 지혜: Compose안 | 지혜·오현·연결 담당 | 서비스명·포트·환경변수 이름·build 경로·볼륨·healthcheck |
| C08 | 각 기능 ↔ 시험 | 원민: 사례/기대 결과안 | 해당 기능 담당 | 입력·사전 조건·판정·명령·재현·실패/재시험 |
| C09 | 개인 산출물 ↔ 팀 통합 | 오현: 통합 시점·필요 자료 | 전원 | PR·승인·배포 커밋·보고서·제출 취합 |

C01~C07은 해당 연결을 구현하기 전에 맞춘다. C08의 기대값은 기능 구현 전 작성하고, C09는 단계별 통합에서 반복한다.
임베딩 모델과 벡터 차원은 유빈님이 수업 설정을 확인해 제안하고 지혜님이 스키마에 반영한다. 모델/차원이 바뀌면 벡터 호환성·재색인 영향도 함께 검토한다.
웹 API 계약의 JSON과 가능한 OpenAPI 초안은 지혜님 폴더에서 만들고, 오현이 공통 기준으로 취합한다.

## 3. 상대를 기다리는 동안 할 일

| 담당 | 먼저 진행 가능 | 실제 연결 전에 필요한 것 |
| --- | --- | --- |
| 수언 | 화면 목록·상태 디자인·프로젝트 골격, 합의한 예시 기반 Mock | C01의 공통 반영과 지혜님의 실제 API |
| 지혜 | API/스키마 제안·서버/DB 실행 골격·인증 설계 | C06 차원/메타데이터 합의 후 벡터 스키마 확정, C02/C05 후 실제 연결 |
| 다혁 | 공통 입력·차단·출력 골격·역할 카드 | C03/C04의 공통 반영과 search/handoff 실제 응답 |
| 유빈 | 문서/권한 목록·청킹 후보·검색 평가 질문 | C06 DB·차원 확정 후 색인, C03 후 본체 연결 |
| 원민 | 시험 기대값·시연 입력·기본 data-api 이관 시험 | C04/C05 후 실제 이관·FastAPI 저장 연동 |
| 오현 | 소유권·공통 문서·PR/마일스톤·검토 순서 관리 | 전원 실행 정보와 확인 결과 후 VM 통합 |

기다리는 대상은 연결에 필요한 계약·실제 서비스다. 이를 이유로 독립적으로 할 수 있는 문서·골격·Mock·시험 기대 작성까지 멈추지 않는다.
확정되지 않은 JSON을 각자 다르게 확정해 구현하지 않는다.

## 4. 실제 협의 절차

1. 제안자가 자기 Doc/HANDOFF.md에 연결 ID·입출력 예시·권한·오류·버전·영향·상대가 수정할 파일을 적는다.
2. 상대는 이를 읽고 **자기 HANDOFF**에 수용/수정안·이유·반대편 링크를 적는다. 상대 문서를 직접 편집하지 않는다.
3. 합의한 두 기록을 오현에게 전달한다. 기록에는 상대의 실제 확인 근거를 남기며 대답이 없다는 이유로 동의 처리하지 않는다.
4. 오현이 docs/API-CONTRACT 등 공통 기준을 반영하고 커밋/문서 절을 알린다.
5. 각자 최신 기준을 읽고 자기 SPEC·계획을 갱신한 뒤 구현한다.
6. 실제 요청을 서로 보내 연결을 확인한다. 결과·입력·실패·재시험을 자기 기록에 남긴다.
7. 불일치가 있으면 소유자에게 재현 요청한다. 소유자 수정 PR과 관련자 재시험 뒤 통합한다.

이는 팀원의 실제 협의를 진행하는 절차다. 저장소에 양식이 있다고 협의가 끝난 것은 아니다.
연락 도구는 팀이 사용 중인 채널을 이용하고 최종 합의 근거를 파일에 남긴다. 이 문서 작성 과정에서 팀원에게 메시지를 전송하지 않았다.

## 5. P0 → P1 → P2·병합 순서

| 단계 | 병렬로 준비 | 연결·병합 기준 |
| --- | --- | --- |
| P0 | 요구·계약, 화면 Mock, API/DB/pgvector 골격, 본체 입력 골격, 시험 기대 | 계약 PR(오현) 먼저 → 각자 범위의 골격 PR → 실제 실행 근거 확인 |
| P1 제공자 기능 | 지혜 API·저장, 유빈 index/search, 원민 handoff/errors, 다혁 본체, 수언 화면 | 각자 단독 확인. 소비자는 합의한 Mock으로 개발 |
| P1 실제 연결 | C02~C06 기반 제공자/소비자 연결 | 관련 제공자 계약·실제 응답 확인 → 본체/웹 연결 PR → 공통·통합 시험 |
| P1 안정화 | 권한·중복·보안·장애·복구·반복·성능 | 필수 회귀·실패/재시험·VM 재현 근거 |
| P2 | 필수 확인 뒤 선택한 고도화 | 오현이 범위/일정 조율, 81일차 8교시 기능 동결 |
| 제출 | 실측·개인 설계 자료·보고서 취합 | 오현이 루트 제출 경로·문서·버전 검토 |

정상 경로만 구현한 상태는 P1 완료가 아니다. 고정 날짜·첫 통합 시각과 GitHub 마일스톤은 오현이 팀 상황에 맞춰 등록한다. 현재 등록됐다고 표시하지 않는다.

## 6. PR과 확인 결과

- 브랜치: feat/<개인폴더>-<작업명>. 한 PR은 한 단계 또는 한 기능으로 작게.
- 일반 담당자 PR에는 자기 폴더만 포함한다. 이름 변경·루트 설정·공통 계약은 개인 요청으로 직접 수정하지 않는다.
- 필수 PR 내용: 요구 ID / 연결 ID·기준 버전 / 수정 파일 / 실제 확인 명령·결과 / Mock 사용 / 미해결 문제.
- 오현이 PR 경로와 계약 영향·확인 근거를 검토해 병합한다. 충돌이 나면 담당자와 경로를 확인하고 자기 파일에서 해결한다.
- 팀 VM은 오현이 기본 브랜치에서 배포한다. 다른 사람의 로컬 n8n에 무작정 전체 JSON을 push하지 않는다.
- 실제 자동 CI·브랜치 보호·폴더 접근 차단은 아직 설정 완료로 간주하지 않는다.

개인별 구체 작업은 각 폴더의 Doc/WORK-GUIDE.md를, 실제 전달 기록은 Doc/HANDOFF.md를 따른다.
