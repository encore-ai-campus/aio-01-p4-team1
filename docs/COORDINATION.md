# 기본안 적용과 변경 협의

> 운영 방식: 팀장이 공통 기준을 먼저 배포한다. 담당자는 그 기준대로 자기 폴더에서 개발하고, 기준을 바꾸려 할 때만 아래 상대와 협의한다.

## 1. 먼저 읽을 기준

- 주제·저장소: [TOPIC](TOPIC.md).
- 공통 웹훅과 웹 API 경로: [API-CONTRACT](API-CONTRACT.md).
- 연결 JSON·실행 환경: [공통 API](API-CONTRACT.md).
- 사용할 데이터·업무/벡터 테이블 기준: [DATA-AND-DB](DATA-AND-DB.md).
- 공통 14종 시나리오·검증 기준: [EVALUATION-GUIDE](EVALUATION-GUIDE.md).

배포된 공통 기준대로 구현하는 데 담당자 간 재승인은 필요 없다.
설계안을 바꿀 때와 실제 연결에서 계약 불일치가 발생했을 때만 변경 협의한다.
기술 세부안을 전부 팀원끼리 처음부터 정하도록 요구하지 않는다.

## 2. 파일 소유권

이름별 편집 경로는 [팀 헌장](TEAM-CHARTER.md)의 역할표를 따른다. 일반 담당자는 자기 폴더만 수정한다.
공통 문서·계약·제출 취합은 오현님, DB 마이그레이션은 지혜님 담당이다. 역할별 상세 작업은 각자의 README·IMP-PLAN에 있다.

이 표는 매번 협의해야 하는 할 일 목록이 아니라 **변경 시 연락할 책임표**다.
공통 웹훅 계약·공통 시나리오 판정은 기본안에서도 바꾸지 않는다.

## 4. 개발 순서

1. 팀장이 배포한 기준을 읽고 자기 TODO·SPEC·IMP-PLAN에 적용한다.
2. P0에서 자기 실행 골격·입력/출력 예시·Mock·시험 기대를 만든다.
3. API/검색/이관 등 제공자가 자기 기능을 구현하는 동안 소비자는 같은 예시 Mock으로 병렬 개발한다.
4. 제공자 실제 응답이 준비되면 Mock을 실제 주소로 교체하고 서로 요청을 보내 검증한다.
5. 정상·권한·중복·장애·복구를 확인하고 작은 PR로 제출한다.
6. 오현님이 검토·병합·팀 VM 배포·회귀 시험과 결과 취합을 관리한다.
7. 필수 완료 뒤 고도화, 81일차 8교시 기능 동결, 82일차 시험·수정·문서·발표.

상대의 구현 완료를 기다리는 것과 설계를 다시 협의하는 것은 다르다. 실제 서비스가 없을 때는 Mock으로 개발한다.
실측해야 하는 검색 신뢰도·처리시간은 임의 PASS 수치로 고정하지 않고 측정 뒤 문서에 반영한다.

## 5. 기준 변경 절차

1. 변경이 필요한 담당자가 자기 HANDOFF에 연결 ID·기존 값·변경안·이유·입출력·영향을 적는다.
2. 표의 상대는 자기 HANDOFF에 검토 결과·반대편 링크를 남긴다. 대답이 없다는 이유로 동의 처리하지 않는다.
3. 오현님이 영향과 공통 기준을 확인해 공통 문서를 수정하고 기준 커밋을 알린다.
4. 각자는 자기 SPEC·코드만 수정하고 관련 연결/회귀를 재시험한다.
5. 상대 코드 버그는 재현 입력·기대/실제·로그를 전달하고 파일 소유자가 수정한다.

변경 요청이 없다면 HANDOFF를 먼저 채워야 개발할 수 있는 것이 아니다.
일반 PR은 자기 폴더만 포함한다. 실제 OS 접근 차단·GitHub CI·브랜치 보호를 설정 완료한 상태는 아니다.

## 6. 개인 개발과 통합 확인

개인 작업 순서는 TODO(무엇을·왜) → SPEC(입력·기대 결과) → IMP-PLAN(단계·파일·확인 명령) → 한 단계 구현 → 직접 확인 → 커밋이다.
공통 기준을 그대로 적용하는 과정에 별도 계약 합의 단계를 추가하지 않는다. 정상·권한·오류·경계 조건을 확인하고, 실제 결과와 미실행을 구분한다.
n8n JSON은 에이전트가 check하고 push·test는 사람이 수행한다. 팀 VM은 오현님이 기본 브랜치에서 배포하고 매 배포 뒤 공통 회귀를 확인한다.

공통 워크플로우 시험은 data-api 기준으로 먼저 수행하고, FastAPI 어댑터·DB 저장은 별도 통합 시험으로 확인한다.
data-api의 고장 스위치는 FastAPI에 자동 적용되지 않는다. fault/reset/ops 대상과 실제 호출 대상을 맞추고, 같은 본체에 설정으로 연결한다.
웹·서버·DB는 자기 README의 실제 설치·실행 명령으로 검증한다. 일반 PR에는 자기 폴더만 담고 요구 ID·계약 ID·실제 결과·Mock 사용·미해결 문제를 적는다.

각 역할의 개발 문서는 최종 제출 문서를 대신하지 않는다. 설계서에는 실제 노드·연결선, RAG 설계서에는 실제 비교 수치, 결과서에는 실제 runs 보고서를 반영한다.
기능 코드·JSON·데일리·측정·시험 결과는 아직 작성/실행 전인 부분을 완료로 표시하지 않는다.
