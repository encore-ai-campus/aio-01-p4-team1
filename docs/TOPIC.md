# 오케퐁 사내 IT 헬프데스크 · 주제 제안서

> 이 문서는 80일차의 주제와 구현 계획을 정리한 제안서다. 이후 확정된 검색 기준은 2절에 구분해 적었다. 실제 구현·시험 결과는 [실행 결과서](EXECUTION-RESULT.md), 주제 승인 근거는 8절에서 확인한다.

## 1. 주제와 해결할 문제

오케퐁 직원 6명이 반복적인 사내 IT 문제의 근거 있는 해결 절차를 빠르게 받고, 자동 답변할 수 없는 문의는 IT팀에 정확히 접수되도록 한다.

- 사용자: 제공된 가상 직원 6명. IT팀 김민지·정우성은 관리자 역할을 맡는다.
- 구현 조합: 선생님 분류의 C형(Next.js 직원·관리자 화면 + FastAPI + n8n). 먼저 A 기본 동작으로 공통 시나리오를 확인한 뒤 웹 화면과 API를 연결한다.
- 추가 기능: 텔레그램 입구는 필수 기능과 시연이 완성된 경우에만 검토한다.

## 2. 기술 지원 범위

| 문의 유형 | 근거 자료·예 | 처리 원칙 |
| --- | --- | --- |
| 계정·인증 | 비밀번호 재설정, 계정 잠김 | 규정의 절차를 안내하고 직접 계정 조치는 이관 |
| 네트워크·VPN | VPN 접속 오류 | 근거를 찾아 안내 |
| 메일·문서·개인정보 | 메일함, 문서 공유, 개인정보 규정 | 권한이 허용된 문서만 근거로 사용 |
| 기기·프린터·회의실 | 장비 문제, 프린터, 회의실 장비 | 자가 점검 안내, 현장 조치 필요 시 이관 |
| 소프트웨어 | 설치·사용 문의 | 승인·사용 절차 안내, 실제 설치 요청은 이관 |
| 보안 사고 | 피싱, 기기 분실, 유출 의심 | 긴급 티켓·알림, 규정에 있는 초동 조치만 안내 |

자동 답변은 사용자가 볼 수 있는 근거가 검색되고 검증을 통과할 때만 한다. 정보가 부족하면 보완 질문을 하고 `attempt >= 3`이면 이관한다. 근거가 없거나 검증에 실패하면 추측하지 않고 이관한다.

검색 점수 기준은 제안 당시 실측 후 정할 계획이었다. 이후 main에 적용한 자동 답변의 근거 최소 점수는 **0.40**이다. 점수 외에도 문서 권한·근거 내용·답변 검증을 통과해야 한다. 선정 근거와 측정 한계는 [RAG 설계서의 유사도 측정 및 0.40 기준](RAG-ARCHITECTURE.md#유사도-측정-및-040-기준)을 따른다.

## 3. 데이터와 저장

- 제공 data-api: 규정 8종, FAQ 6종, 가상 직원 6명, 기존 티켓 4건 및 공통 시험의 데이터·장애 조건에 사용한다.
- 오케퐁 PostgreSQL: 새 문의, 티켓, 알림, 계정, 세션, 처리 상태를 저장한다.
- RAG: 제공 규정을 청킹·임베딩하고 PostgreSQL의 pgvector에 저장·검색한다. 업무 데이터와 문서 청크·벡터는 테이블을 분리한다. `oke-index`로 색인·갱신하며 재시작 후에도 저장 데이터가 유지되도록 구성한다.
- MongoDB·InfluxDB는 이번 필수 구현 범위에 넣지 않는다. pgvector는 RAG 구현 범위에 포함한다.

## 4. 화면·계정·티켓

- 직원: 로그인 → 질문 → 답·근거 또는 이관 결과 → 내 문의·티켓 상태 확인.
- 관리자: 직원 계정 생성·비활성화·비밀번호 초기화, 티켓 목록·긴급 알림 확인, 담당자·답변·상태 변경.
- 공개 회원가입은 없다. 첫 관리자 계정을 안전하게 준비한 뒤 관리자가 제공된 나머지 직원의 계정을 만든다. 임시 비밀번호는 첫 로그인 때 변경한다.
- 티켓 상태는 `접수 → 처리 중 → 완료`, 긴급도는 `보통`·`긴급`으로 시작한다. 같은 `request_id`의 티켓은 한 번만 생성한다.
- 화면은 FastAPI만 호출한다. FastAPI는 로그인·권한·입출력 검증·저장과 n8n 호출을 담당하고, n8n은 분류·RAG·답변·검증·이관 판단을 담당한다.

## 5. 역할과 80일차 준비

오현님은 범위·계약·병합·VM 배포·제출을, 수언님은 화면을, 지혜님은 FastAPI·업무 DB·실행 환경을, 다혁님은 문의 본체를, 유빈님은 색인·검색을, 원민님은 이관·오류·시험을 맡는다. 세부 파일·문서 책임은 [팀 헌장](TEAM-CHARTER.md)을 따른다.

### C형 화면·API 연결 계획

아래는 당시 제안한 연결 순서와 담당이다. 현재 구현·시험 완료 여부와는 구분한다.

| 항목 | 담당·계획 |
| --- | --- |
| 직원·관리자 화면 → FastAPI | 수언님이 화면과 API 호출을, 지혜님이 로그인·권한·저장 API를 담당 |
| FastAPI ↔ n8n | 지혜님이 API 연결을, 다혁님이 문의 처리 워크플로우를, 원민님이 이관·오류 처리를 담당. 오현님이 통합·배포 |
| A 기본형 공통 시험 | 같은 `oke-support`와 data-api로 먼저 확인한 뒤 화면·API를 연결. 당시 제안서에는 시험 완료 목표 교시·시각이 기록되지 않아 소급해 채우지 않음 |
| 화면·API 연결이 늦어질 때 | 같은 `oke-support`를 웹훅으로 호출해 시연 |

공식 공통 시험과 서비스 연결 시험의 실제 수행 범위·결과는 [실행 결과서](EXECUTION-RESULT.md)에서 구분해 확인한다.

### 80일차 준비 목표

- 5교시에는 워크플로우 설계서 1~4절과 팀 사례 5개 초안, 6교시에는 색인 수·청크 길이 분포와 RAG 설계서 1~2절을 준비한다.
- 7교시 첫 VM 배포, 8교시 설계 초안·VM 동작 발표와 DAY80 기록을 목표로 한다. 실제 완료는 실행 근거로 기록한다.

## 6. 공통 시나리오 질문 예시

## 7. 주제 설명 · 1분 발표문

우리 팀은 오케퐁 직원 6명을 위한 사내 IT 헬프데스크를 만들겠습니다. 직원이 웹에서 로그인해 비밀번호·VPN·메일·장비 문제를 질문하면, AI가 권한이 허용된 사내 규정을 찾아 근거와 함께 안내합니다. 정보가 부족하면 보완 질문을 하고, 근거가 없거나 실제 조치가 필요하면 IT팀 티켓으로 이관합니다. 피싱·유출 같은 사고는 긴급 접수와 알림을 우선합니다. 제공된 규정 8종·FAQ 6종·직원 6명·기존 티켓 4건을 활용하며, 새 계정과 문의·티켓은 PostgreSQL에, 문서 임베딩은 pgvector에 저장합니다. 공통 시험을 지키면서 직원 질문부터 관리자 처리까지 연결하는 것을 목표로 합니다.

## 8. 착수 당시 점검과 주제 승인 기록

아래 체크 상태는 기존 제안서의 기록을 보존한 것이다. 빈 칸은 이 문서에 확인이 기록되지 않았다는 뜻이며, 현재 기능의 미구현·시험 미수행을 뜻하지 않는다. 현재 동작과 시험 근거는 [실행 결과서](EXECUTION-RESULT.md)를 따른다.

- [ ] 기업의 기술 지원 업무, 지식 문서, 사람 이관, 권한·개인정보, 외부 장애 조건을 설명할 수 있다.
- [ ] 공통 웹훅 계약과 공통 시나리오를 유지한다.
- [x] 화면·FastAPI·PostgreSQL·로그인과 워크플로우의 주 담당·파일 소유 경로를 문서에 배정했다.
- [x] 주제 승인 완료 상태를 아래 근거에 따라 반영했다.
- [ ] 팀 전체가 조합과 주제 제안서의 최종 범위를 확인한다.

주제 승인 근거는 81일차 공식 체크리스트의 “80일차 2교시 주제 승인 완료 기록 유지” 안내다. 승인 완료 상태를 반영하되, 80일차 원본 체크박스가 체크됐다고 주장하지 않는다. 확인자와 정확한 승인 시각은 미기록이다. 개별 기능 예외·계약 변경은 주제 승인과 별도로 근거를 확인한다.
