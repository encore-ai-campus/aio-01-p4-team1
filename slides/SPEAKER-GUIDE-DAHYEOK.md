권한 격리는 검색 결과를 모두 가져온 뒤 화면에서 숨기는 방식이 아닙니다. 신원을 확인한 백엔드가 허용된 access level을 만들고, 검색 SQL이 벡터 거리 정렬 전에 `WHERE d.access_level = ANY(:verified_access_levels)`로 후보 문서를 제한합니다. 일반 직원의 범위는 `all` 일곱 문서·서른 청크, IT 담당자는 `all`과 `it` 여덟 문서·서른세 청크입니다. 실서버 WF-05 측정에서 동일 보안사고 질의 시 일반 직원 범위로 IT 전용 문서가 새어 나온 건수는 0건이었고, IT 범위에서는 정상 2건이 반환됐습니다. 또한 FastAPI는 `HttpOnly` 세션 쿠키와 RBAC로 비로그인 401, 직원 로그인 200, 직원의 관리자 티켓 접근 403 차단, 관리자 티켓 200을 엄격히 강제합니다. 나아가 프론트엔드 컨테이너에는 `init=true`, `pids_limit=100`, `/tmp` 및 `/var/tmp` `tmpfs(noexec,nosuid)` 보안 방어벽을 구축해 악성 바이너리(ELF) 실행을 커널 수준(`EACCES`)에서 거절하도록 검증했고, Next 15.5.29, React 19.1.10, sharp 0.35.5, PostCSS 8.5.32 핀 고정으로 운영 의존성 취약점 0건을 달성했습니다.

**전환:** 이제 잘못된 입력이나 하위 서비스 장애에서 시스템이 어떻게 안전하게 끝나는지 보겠습니다.

## 예상 Q&A 가이드 (7문 7답)

> 답변 구조: **결론 → 실측 근거 → 설계 경계 → 향후 확장 계획**. 각 질문은 30~45초 안에 명확히 답한 뒤 추가 질문을 받습니다.

### 1. “유사도 0.40은 왜 정했습니까? 0.380도 정상 문서였다면서요?”

**답변:** 0.40은 유사도 점수를 확률로 오해해서 정한 값이 아닙니다. 같은 임베딩 모델과 cosine 검색 조건에서 16개 질문을 측정했을 때 범위 밖 후보 상위 점수는 0.235에서 0.383, 범위 안 기대 문서 점수는 0.380에서 0.709였습니다. 측정된 범위 밖 상단 0.383보다 약간 높은 곳에 게이트를 둬 해당 후보를 자동 답변 경로에서 걸러내려는 선택입니다. 다만 정상 최저 0.380과 범위 밖 최고 0.383은 겹치므로 임계값만으로 정답을 판별한다고 주장하지 않습니다. 실제 자동 답변에는 권한 필터, evidence 내용 확인, Writer 출력, Verifier의 근거성·정책 검증이 모두 필요합니다. 질문 세트도 고정 승인 정답셋은 아니고, VM에서 점수 기반 품질을 재측정한 결과도 아닙니다. 다음 단계는 frozen QA 세트를 확대해 false accept와 false reject를 함께 측정하고, 승인된 기준으로 조정하는 것입니다.

**꼬리 질문 대응:** “그럼 0.40을 낮추면 정상 답변이 늘지 않나요?” → “늘 수 있지만 범위 밖 후보도 통과할 수 있습니다. 정확도·재현율을 고정 세트에서 함께 보고 결정해야 하며, 지금 숫자만으로 낮추는 판단은 하지 않겠습니다.”

### 2. “왜 n8n에서 분기하고 LLM에게 전부 맡기지 않았나요?”

**답변:** 권한, 시도 횟수, 장애 응답, 티켓 생성처럼 결과가 명확하고 감사 가능해야 하는 규칙은 결정적 분기로 처리하고, LLM은 자연어 triage나 답변 초안 같은 해석 작업에 한정했습니다. 모델은 질문을 잘 이해할 수 있지만 같은 입력에도 결과가 달라질 수 있고, JSON 형식이나 근거를 벗어날 수 있습니다. 반면 n8n의 조건과 검증 노드는 attempt가 세 번이면 이관한다거나, 검색 503이면 빈 검색으로 가장하지 않는 규칙을 추적 가능하게 합니다. 모델이 생성한 triage 결과도 파싱 후 허용된 enum과 타입을 검증하고, verifier를 통과해야 답변합니다. 이 구조가 모델 위험을 없애는 것은 아니지만, 모델 오류가 권한이나 티켓 정책을 직접 바꾸지 못하게 제한합니다. 실행 추적을 통해 어느 분기에서 끝났는지 설명할 수 있다는 점도 심사와 운영에 중요합니다.

**꼬리 질문 대응:** “분기를 코드로만 짜면 더 쉽지 않나요?” → “가능합니다. 여기서는 팀의 n8n 통합과 운영 관측 요구에 맞춰 흐름을 시각화했고, 복잡한 정책은 무분별하게 Code 노드에 숨기지 않도록 계약과 노드 책임을 문서화했습니다.”

### 3. “오류가 나면 Error Trigger와 하위 워크플로우 격리는 어떻게 작동합니까?”

**답변:** 저희는 예상 가능한 비즈니스 장애와 예상치 못한 런타임 예외를 이중으로 격리합니다. 첫째, 검색 타임아웃(4초)이나 핸드오프 타임아웃(5초) 같은 하위 호출 장애는 `search_unavailable` 또는 `handoff_unavailable` 상태로 전환해 메인 워크플로우가 죽지 않고 HTTP 200 안전 응답을 반환하도록 설계했습니다. 실제로 1차 실서버 시험에서 `oke-handoff`에 H01 웹훅 누락 장애가 있었을 때도 메인 `oke-support`는 HTTP 200 안전 폴백을 반환해 장애 격리를 증명했습니다. 둘째, 예상치 못한 런타임 예외에 대해서는 `oke-support`, `oke-search`, `oke-handoff` 3개 운영 워크플로우 전원에 `settings.errorWorkflow = "okeErrorsFlow01"`을 영구 바인딩(`0b848e7`)하여 안전 문맥만 추출해 알림과 DLQ에 기록하고, `okeErrorsFlow01` 자체는 `errorWorkflow = ""`로 비워 재귀 호출을 원천 차단했습니다.

**꼬리 질문 대응:** “1차 핸드오프 장애는 어떻게 복구했습니까?” → “원민 님과 함께 VM의 `oke-handoff`가 29노드(H01 웹훅 누락) 상태임을 진단한 뒤 정본 30노드를 재게시하여 총괄 스모크 `T-2033`, WF-09 `T-2034`, WF-02b `T-2035`, WF-03 `T-2036`까지 전 구간 티켓 발급을 정상 복구했습니다.”

### 4. “RBAC와 컨테이너 보안은 실제로 어디서 강제됩니까? 프롬프트에만 있나요?”

**답변:** 프롬프트에만 있지 않고 웹·DB·컨테이너 3중 경계에서 강제됩니다. 첫째, 웹에서는 FastAPI가 `HttpOnly` 세션 쿠키를 검증해 비로그인 401, 직원 로그인 200, 직원의 관리자 티켓 접근 403 차단, 관리자 티켓 200을 강제하며 요청 본문의 부서/역할 주장은 신뢰하지 않습니다. 둘째, RAG에서는 검증된 사용자 권한 범위를 PostgreSQL SQL의 `WHERE access_level = ANY(...)` 사전 필터로 강제해 벡터 유사도 계산 전에 비인가 문서를 원천 배제하며, 실서버 WF-05에서 일반 범위의 IT 문서 노출 0건과 IT 범위 2건 반환을 입증했습니다. 셋째, 11/8 00:04 KST 보안 마감으로 FE 컨테이너에 `init=true`, `pids_limit=100`, `/tmp·/var/tmp tmpfs(noexec,nosuid)` 방어벽을 구축해 악성 ELF 바이너리 실행을 커널 수준(`EACCES`)에서 차단했고, Next 15.5.29 / React 19.1.10 / sharp 0.35.5 / PostCSS 8.5.32 핀 고정으로 운영 취약점 0건을 달성했습니다.

**꼬리 질문 대응:** “팀 이름을 바꿔 보내면 우회되지 않나요?” → “클라이언트 제공 부서가 아니라 서버가 확인한 직원 레코드로 허용 집합(`all` vs `all,it`)을 구성하며, 실서버 영수증 `rag-search-eval-20261107.json`과 `be-db-integration-20261107.json`으로 입증했습니다.”

### 5. “스키마 검증과 재시도는 어떻게 무한 루프나 중복 티켓을 막습니까?”

**답변:** 입력은 `request_id`, `user`, `question`, `attempt`를 타입·필수 여부 기준으로 검사하고, Triage와 최종 응답도 지정된 enum과 스키마로 검증합니다. 보완 질문은 `attempt`로 횟수를 제한해 세 번째 시도(`attempt >= 3`, WF-02b)에서는 추가 질문 없이 즉시 담당자 이관(`T-2035`, 2.188초 PASS)으로 종료합니다. 하위 핸드오프 호출은 5초 타임아웃과 최대 2회 제한 재시도(1000ms 간격)를 적용하며, 동일 `request_id` 재요청은 멱등 키로 중복 생성을 차단합니다. 실제로 실서버 WF-09 2차 재시험(`live-integration-qa-20261107T113546Z.json`)에서 동일 요청을 두 번 호출했을 때 1차 호출은 2.257초 만에 신규 티켓 **`T-2034`**(`duplicate=false`)를 생성했고, 2차 호출은 0.594초 만에 동일한 **`T-2034`**(`duplicate=true`)를 즉시 반환하며 DB `tickets`·`alerts` 중복 증가 0건으로 7/7 검증 항목을 모두 통과했습니다.

**꼬리 질문 대응:** “재시도 횟수는 몇 회입니까?” → “`oke-handoff` 티켓 저장은 5초 예산 내에서 최대 2회(1000ms 간격)로 제한하며, 알림과 DLQ는 각 600ms 타임아웃의 독립 경로로 분리해 티켓 응답을 지연시키지 않습니다.”

### 6. “실서버에서 겪었던 가장 큰 장애와 해결 과정, 그리고 WF-01 응답시간 결과는 어땠습니까?”

### 7. “100배 규모에서 실제로 버틸 수 있습니까?”

**꼬리 질문 대응:** “38.67MiB면 작으니 문제 없지 않나요?” → “그 숫자는 벡터 원시 배열만입니다. 실제 DB 크기와 동시 요청 하의 검색 p95 지연을 함께 검증해 HNSW 인덱스와 커넥션 풀을 튜닝하겠습니다.”
