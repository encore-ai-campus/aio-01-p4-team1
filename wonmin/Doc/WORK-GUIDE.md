# 이원민 · 맡은 일과 협의 순서

> 상태: 팀장이 준비한 작업 지침. 아래 담당·절차를 기준으로 진행한다. 기술 세부안은 지정 상대와 협의 기록을 남기며, 아직 합의·구현·시험이 끝난 것은 아니다.

## 1. 내 작업 범위

workflows/oke-handoff.json·oke-errors.json, cases/·requests/·runs/·자체 시험 도구·Doc. 상대 코드 수정 대신 재현 자료를 담당자에게 전달한다.

**수정·생성·삭제·이동은 `wonmin/` 안에서만 한다.** 루트 docs·README·AGENTS·.env.example·다른 이름 폴더는 읽기만 한다. 상대의 코드를 복사해서 중복 구현하지 않는다. DB 접속·API 호출은 파일 수정 권한과 별개이며 합의한 계약과 자격증명으로 수행한다.

## 2. 반드시 먼저 확인할 것

1. [주제](../../docs/TOPIC.md)와 [공통 API](../../docs/API-CONTRACT.md)를 읽는다. PostgreSQL+pgvector·관리자 계정 발급·6명 역할 배정은 유지한다.
2. [TODO](TODO.md)를 자기 말로 검토하고 [SPEC](SPEC.md)의 요구와 [구현 계획](IMP-PLAN.md)을 구체화한다.
3. 아래 상대에게 보낼 제안은 내 [HANDOFF](HANDOFF.md)에 작성한다. 상대와 협의한 실제 내용·확인 근거만 기록한다.
4. 계약에 영향을 주는 변경은 오현에게 전달한다. **오현이 공통 계약에 반영한 뒤** 해당 연결을 구현한다.
5. 상대 기능이 아직 없어도 합의한 예시를 임시 응답/가짜 데이터로 만들어 자기 기능을 개발한다. 실제 연결 전까지 사용 중인 Mock을 표시한다.

## 3. 누구와 무엇을 협의하나

| 연결 ID | 상대 | 내가 먼저 보낼 것 | 상대에게 받을 것 | 맞춰야 하는 시점 |
| --- | --- | --- | --- | --- |
| C04 | 임다혁 | handoff 입력·티켓/실패 응답·중복·알림 결과·Error Workflow 연결 정보를 제공한다. | 이관 사유·긴급도·request_id와 본체 시간 제한 | 이관 본체 연결 전 |
| C05 | 박지혜 | 티켓·알림 저장·조회·인증·재시도·중복·DLQ 관측 요구를 제안한다. | 호환 API 예시·실패 상태·내부 인증·DB 확인 방법 | FastAPI 이관 연결 전 |
| C08 | 전 담당자 | 시나리오 입력·사전 조건·기대 결과·실패 재현 방법·보고서를 제공한다. | 자기 기능의 기대 결과와 실행 방법, schema/version 정보 | 구현 전 기대 작성·구현 뒤 확인 |
| C09 | 오현 | 전체 통과 수·실패/재시험·실제 보고서·캡처·시연 요청을 제공한다. | 팀 VM 회귀 시점·최종 제출 기준 | 매일 통합·동결·제출 전 |

협의할 때 “완성되면 알려주세요”로 끝내지 않는다. **입력 JSON·성공 JSON·실패 JSON/HTTP 상태·권한·시간 제한·버전·확인 방법**을 함께 맞춘다.
DB 연결은 테이블/컬럼·벡터 차원·거리·권한·마이그레이션 순서, 실행 환경은 서비스명·포트·환경변수 이름·실행 위치까지 적는다.
환경변수 실제 값·비밀번호·토큰은 기록하지 않는다. 협의 기록과 공통 반영은 [팀 협업 절차](../../docs/COORDINATION.md)를 따른다.

## 4. 개발 순서와 끝내는 기준

| 단계 | 할 일 | 끝내는 기준 |
| --- | --- | --- |
| P0 | C04/C05를 맞추고 공통 14유형을 읽어 팀 시나리오 기대를 먼저 작성한다. | 키트 원본 기대 유지·팀 정상/경계/권한/이관/장애 입력 초안 |
| P1-1 | data-api 기준 handoff·중복·재시도·DLQ·알림을 구현한다. | 정상/500/timeout/중복 응답과 ops 관측 일치 |
| P1-2 | errors를 지정·게시하고 FastAPI 연동 설정을 따로 검증한다. | 같은 본체의 설정 전환, 실제 FastAPI 저장·권한·중복 검증 |
| P1-3 | 공통·팀·LLM 반복·장애·성능·VM 회귀와 시연을 정리한다. | 가짜 PASS 없이 실패/재시험 포함, 고장 해제·마스킹 확인 |

단계 크기는 혼자 설명하고 확인할 수 있는 PR 한 건으로 쪼갠다. 위 표는 개인 개발의 진행 순서이며, 각자 모든 기능을 완성한 뒤 한 번에 연결하지 않는다.
관련 계약이 반영되고 제공자 예시 응답이 확인되면 연결 PR을 만든다.
P1에는 권한·개인정보·오류·중복·복구 등 필수 안정성도 포함한다. P2는 P1 검증 뒤 팀장이 범위를 정한다.

## 5. 내가 내야 할 결과물

이관/오류 JSON, 팀 5개 이상 시나리오, 시연 입력, 공통·팀·반복·장애·bench 실제 보고서, 실패/재시험 기록. 결과서 제공 자료는 wonmin/Doc/SUBMISSION-NOTES.md에 적는다.

루트 제출 문서는 직접 수정하지 않고 자기 Doc/SUBMISSION-NOTES.md에 **반영할 문서·절 / 실제 설계 / 측정·보고서 경로 / 남은 문제**를 정리해 오현에게 넘긴다.
코드·JSON은 담당자가 구현한 뒤 생성한다. 확인하지 않은 노드·수치·PASS를 채우지 않는다.
기능을 완성하면 자기 README에 설치·실행·확인 명령과 상대 서비스가 필요한 조건을 적는다.

## 6. 작업 한 건을 진행하는 방법

1. 최신 main 기준으로 `feat/wonmin-작업명` 브랜치를 만든다. 미커밋 작업이 있으면 먼저 안전하게 정리한다.
2. 자기 SPEC 요구 ID와 이번 단계·수정 파일·통과 기준을 정한다.
3. 코딩 에이전트에는 자기 폴더와 지정 단계만 허용한다. 공통/상대 파일을 고치려 하면 중단하고 변경 요청을 남긴다.
4. 자신의 기능을 실행해 확인한다. n8n check 뒤 push·test는 사람이 수행하며 개인 로컬 n8n에서 자기 워크플로우만 올린다. 팀 VM 배포는 오현만 한다.
5. `git diff --name-only`, `git diff --cached --name-only`로 수정/스테이징 경로를 확인한다. 일반 담당자는 자기 폴더 밖 파일을 PR에 넣지 않는다.
6. PR에 요구 ID·수정 경로·계약 ID/기준 버전·실제 확인 결과·Mock 사용·남은 문제를 적는다. 리드가 검토·병합하고 통합 시각을 알린다.

폴더 규칙은 Git 작업 절차와 에이전트 지침이다. OS 파일 접근을 기술적으로 차단한 상태는 아니므로 PR에서도 경로를 확인한다.

## 7. 에이전트에 줄 작업 요청

```text
현재 작업 폴더는 wonmin/이고 내 역할은 안정성·이관·시험이야.
루트 AGENTS.md와 docs/TOPIC.md·API-CONTRACT.md·COORDINATION.md,
이 폴더 AGENTS.md·README.md·Doc/WORK-GUIDE.md·SPEC.md·IMP-PLAN.md·HANDOFF.md를 읽어.
내가 지정한 요구 ID와 단계만 진행해. wonmin/ 안에서만 파일을 수정·생성·삭제해.
상대/공통 파일 변경이 필요하면 내 Doc/HANDOFF.md에 요청안만 적고 상대 파일은 고치지 마.
이번 수정 파일·입출력·통과 기준을 먼저 정리하고, 완료 후 실제 검사와 미실행을 구분해 보고해.
```

오현의 공통 파일 정비는 리드 작업으로 허용되며, 해당 공통 경로를 작업 요청에 명시한다.
