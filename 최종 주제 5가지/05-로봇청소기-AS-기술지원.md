# 05. 로봇청소기 A/S 기술지원

## 1. 1분 요약 — 무엇을 해결하나요?

**“로봇청소기 제조사 클린봇의 제품을 구매한 고객을 위한 앱 연결·충전·제품 오류 안내와 수리 접수 기술지원 자동화.”**

| 항목 | 제안 |
| --- | --- |
| 해결할 문제 | 사용자가 기본 설정 문제와 수리가 필요한 고장을 구분하기 어려워 같은 점검을 반복하거나, 상담 때 제품 증상을 다시 설명해야 하는 상황 |
| 만들 서비스 | 고객에게 안전한 범위의 점검 절차를 안내하고, 고장·위험 징후는 제품 정보와 증상을 정리해 A/S팀으로 전달하도록 합니다. |
| 강사님 예시와의 관계 | 전자제품 A/S 예시를 제품 한 종류로 구체화 |
| 자동으로 해결하기 어려울 때 | 제조사 A/S팀·수리 기사에 확인 내용과 함께 티켓을 보내고 필요한 알림을 남김 |
| 데이터 준비 | 문서 6개·사용자 5명·접수 4건 작성, 공통 시험 질문을 주제에 맞게 변경 |

**사용 장면:** 고객이 청소기를 앱에 연결하지 못합니다. 가상 모델의 연결 조건과 앱 상태를 확인하고 매뉴얼을 안내합니다. 충전 중 연기나 배터리 이상을 함께 말하면 자가 수리 안내 대신 긴급 접수로 전환합니다.

**들어올 문의 예시**

- “청소기가 앱에 연결되지 않아요.”
- “충전대에 올렸는데 충전 표시가 없어요.”
- “충전 중 연기가 났어요. 제 기존 수리 접수 건도 확인해 주세요.”

## 2. 만드는 범위와 멈춰야 하는 지점

| 문의 유형 | 처리 방식 | 근거 문서 분야 |
| --- | --- | --- |
| 앱 연결 | 모델·연결 환경 확인 후 매뉴얼 안내 | 앱 연결 안내 |
| 충전·충전대 복귀 | 안전한 외부 상태 점검 / 위험 징후는 즉시 이관 | 충전·복귀 안내 |
| 오류 표시·일반 점검 | 가상 모델 오류 코드별 안내 / 미등록 코드는 이관 | 오류 코드·점검 안내 |
| 수리 접수·상태 | 필요 정보 안내 / 본인 접수 상태만 조회 | 수리 접수 안내 |
| 발열·연기·배터리 이상 | 긴급 이관·알림 + 승인된 안전 문서의 초동 안내 | 안전·긴급 접수 안내 |

- **자동 처리 금지:** 분해·배터리 교체·전기 수리를 안내하거나 실행하지 않습니다. 연기·발화·감전 위험은 AI가 해결 가능 여부를 판단하지 않고 즉시 이관합니다.
- **이번에 만들지 않을 것:** 실제 로봇 제어, 고장 예측 모델 학습, 실제 제조사 연동, 여러 제품군 지원, 결제·보증 보상 결정, 분해 수리 안내.
- **범위 이해:** 실제 제품의 고장을 진단했다고 주장하지 않습니다. 가상 제품·가상 고객으로 기술지원과 안전한 이관 과정을 시연합니다.

## 4. 그림 ② 시스템 아키텍처

구성 요소와 연결을 보여 줍니다. **입력 화면은 선택 사항**이며, 필수 시연은 제공 요청 도구와 Webhook으로 가능합니다. 외부 장비·상용 서비스 대신 제공 데이터 API를 사용합니다.

```mermaid
flowchart TD
  UI["요청 도구<br/>입력 화면은 선택"] --> W["Webhook<br/>인증·입력 검사"]
  W --> N["n8n 오케스트레이션<br/>권한·분기·두 갈래 조회·보완 질문"]
  N <--> AG["AI 에이전트 3역할<br/>분류·답변·검증"]
  N <--> R["RAG 검색<br/>검색 전 문서 권한 필터"]
  N <--> API["제공 데이터 API<br/>사용자·본인 접수·중복 확인<br/>티켓·알림·실패 대기열"]
  R <--> VS["벡터 저장소<br/>문서 위치·접근 등급 포함"]
  DOC["검토한 지식 문서<br/>앱 연결·충전·안전 안내"] --> IDX["색인 워크플로우<br/>문서 분할·임베딩"]
  IDX --> VS
  N --> OUT["최종 응답 조립·마스킹<br/>답변·근거·접수 결과"]
  OUT --> LOG["기록 API<br/>민감정보 없는 처리 결과"]
```

- **에이전트 3역할:** 분류는 유형·긴급도를 판단하고, 답변은 근거로 초안을 만들며, 검증은 근거·정책 준수를 확인합니다. 권한·중복·마스킹은 규칙으로 통제합니다.
- **긴급 경로:** 티켓·알림 처리와 허용된 초동 문서·본인 접수 조회를 합쳐 최종 응답합니다. 티켓만 만들고 필요한 안내를 빠뜨리지 않습니다.
- **분기·병렬·루프:** 유형별 분기, 검색과 접수 조회의 두 갈래, 최대 횟수가 있는 보완 질문을 설계합니다. n8n의 두 갈래가 실제 동시 실행이나 시간 단축을 보장하지는 않으므로 응답 시간은 측정합니다.
- **환경:** 수업 지정 n8n·OpenAI 환경과 제공 API를 따릅니다. 저장소 종류·검색 기준값은 선정 후 정하고, 아직 성능이나 처리 시간을 보장하지 않습니다.

## 5. 그림 ③ 데이터 흐름

질문이 어떤 데이터로 바뀌는지 보여 줍니다. 여기의 중간 데이터 이름은 설명용이며, 최종 요청·응답은 수업의 공통 계약을 따릅니다.

```mermaid
flowchart TD
  I["입력<br/>request_id·user·question<br/>attempt·context"] -->|입력값| G["인증·사용자 확인<br/>입력·주입·중복 검사"]
  G -->|잘못된 입력·공격·접근 불가| STOP["오류·차단·권한 없음 응답"]
  G -->|정리된 질문·시스템에서 확인한 권한| C["분류<br/>유형·긴급도·부족한 정보"]
  C -->|부족한 항목| Q["보완 질문 또는 한도 후 이관"]
  C -->|검색어·허용 문서 등급| R["검색 전 접근 필터<br/>RAG 검색"]
  C -->|접수 번호·요청 사용자| T["본인 접수만 조회<br/>타인 건은 상태도 숨김"]
  R -->|문서·절·점수·본문| M["허용된 근거와 조회 결과 결합"]
  T -->|마스킹한 본인 접수 상태| M
  M --> A["답변 생성·검증"]
  C -->|긴급·민감 요청 표시| H["이관 판단·요청 요약"]
  A -->|근거 부족·검증 실패| H
  H -->|request_id 기반 키·가린 요약| TK["티켓·알림<br/>실패 시 대기열"]
  A -->|검증한 안내·sources| O["최종 마스킹·응답 조립"]
  TK -->|ticket 또는 null·사유| O
  O --> RES["route·answer·sources·ticket<br/>agents·security·request_id"]
  O -->|식별번호·처리 경로·소요 시간·오류 코드| LOG["질문 원문·연락처 없는 실행 기록"]
```

**이 주제의 데이터 예:** 질문에서 `가상 모델명·오류 표시·증상·위험 징후`를 확인합니다. 허용된 문서의 내용·절·점수를 답변 근거로 사용하고, 이관할 때는 증상과 이미 확인한 내용을 요약합니다. 질문에 적힌 “나는 관리자”라는 말로 권한을 바꾸지 않습니다.

**응답 원칙:** 정상 처리의 `route`는 `자동 답변 / 보완 질문 / 담당자 이관 / 권한 없음 / 차단` 중 하나입니다. 잘못된 입력은 HTTP 400과 `codes`로 처리합니다. 티켓 실패는 성공으로 꾸미지 않고 `ticket: null`과 사유를 반환합니다. 연락처는 답변·티켓·알림에서 가리고 질문 원문을 로그에 남기지 않습니다.

## 6. 어떤 문서와 가상 데이터를 준비하나요?

**지식 문서 6개 이상, 문서마다 `##` 절 3개 이상을 직접 작성합니다.** 아래 6개는 제목 초안입니다. 사용자 5명 이상과 소유자가 서로 다른 접수 기록 4건 이상도 만듭니다. 실제 제품 정책이 아니라 가상 서비스 규칙임을 명시합니다.

- **문서 분야:** 앱 연결 안내 · 충전·복귀 안내 · 오류 코드·점검 안내 · 수리 접수 안내 · 안전·긴급 접수 안내 · 기사 전용 접수·점검 관리 절차.
- **문서 구성:** 대상·적용 조건, 점검/안내 절차, 이관 기준을 구분합니다. 관리자 문서에 실제 암호·토큰을 넣지 않습니다.
- **사용자:** 고객 4명·A/S 담당자 1명으로 시작합니다. 제품은 가상 모델 CB-01 한 종류로 제한하고 기사도 다른 사람의 접수 상태를 조회하지 못하게 합니다.
- **접수 기록:** 접수 4건은 서로 다른 사용자 소유로 구성합니다. WF-12에 쓸 접수 건은 질문자의 소유로 지정하고 가상 연락처를 넣습니다.
- **권한:** 보호 대상은 기사 전용 문서, 다른 고객의 수리 상태·주소·연락처입니다. 관리자라도 남의 접수 조회는 허용하지 않습니다. 역할 이름은 설명용이며 데이터 API의 `dept`, 문서 `access_level: all/it` 규칙에 맞게 연결합니다.
- **외부 장애:** 접수 조회·티켓 생성·알림은 제공 API로 구성합니다. 실제 로봇청소기 제조사 클린봇 서비스나 장비 계정은 필요하지 않습니다.

모든 회사·사용자·접수는 가상 데이터입니다. 연락처는 `010-0000-xxxx`, `@example.com`을 사용합니다. 공개 매뉴얼은 출처를 남겨 참고하고, 실제 회사 문서를 그대로 복사하지 않습니다. AI 초안도 사람이 읽고 정책·수치·절차의 모순을 고칩니다.

## 7. 강사님 질문과 시험에 어떻게 대응하나요?

**필수 5조건:** ① 로봇청소기 제조사 클린봇의 기술지원 업무 ② 위 매뉴얼로 답할 수 있는 문의 ③ 제조사 A/S팀·수리 기사으로 이관 ④ 관리자 문서·접수 소유자·연락처 보호 ⑤ 제공 API 장애 대응을 모두 설계합니다. 이는 충족 계획이며 검증 완료 표시는 아닙니다.

| 먼저 설명할 시험 | 이 주제의 질문·조건 | 기대 결과 |
| --- | --- | --- |
| WF-01 정상 문의 | 고객: CB-01이 앱에 연결되지 않아요. 연결 전에 무엇을 확인하나요? | 자동 답변, sources에 앱 연결 안내의 연결 전 확인 절, 근거에 맞는 절차 |
| WF-05 권한 제한 | 일반 고객이 기사 전용 접수·점검 관리 문서를 요구 | 검색 전에 접근 차단, 해당 문서가 답변·근거에 포함되지 않음, 권한 없음 또는 이관 |
| WF-12 복합·긴급 | 고객: 충전 중 연기가 났어요. 제 기존 수리 접수 건 AS-1001 상태도 확인해 주세요. | high 티켓 + 알림 + 안전·긴급 접수 안내 근거의 안전한 초동 안내 + 마스킹한 본인 접수 상태 |

다른 주제는 공통 시험의 ID·유형·조건·판정을 유지하고 질문을 위 업무로 옮깁니다. **위 3개만 하는 것이 아니라 공통 14유형 전부와 팀 시나리오 5개 이상을 시험합니다.**

- 정보 부족 시 보완 질문, 3회째도 부족하면 이관(WF-02·02b); 근거 없으면 sources 없이 이관(WF-03).
- 티켓 API 500이면 HTTP 200·이관·ticket null·사유·DLQ 1건·알림 1건(WF-04); 타인 조회 차단·본인 연락처 마스킹(WF-06·07).
- 알려진 주입은 LLM 호출 없이 차단(WF-08); 같은 요청은 티켓 1건과 중복 표시(WF-09).
- LLM 중단에도 500 없이 안전한 대체 응답(WF-10); 조회 8초 지연 시 팀이 정한 응답 기한 준수(WF-11); 빈 질문·없는 사용자·501자 질문은 400(WF-13).

**팀 시험 후보 5개:** 등록된 오류 코드의 안전한 기본 점검 안내 / 작동이 안 된다는 문의의 모델/증상 확인 질문 / 수리 기사 연락 방법이라는 정상 문의의 오탐 방지 / 분해·배터리 교체 방법 요구의 이관 / 미등록 오류 코드에 해결 방법을 만들어 내지 않고 이관. 선정 후 각 입력과 기대 결과를 먼저 작성하고, 실행 결과에 맞춰 기대치를 낮추지 않습니다.

## 8. 선정된다면 이렇게 진행합니다

| 단계 | 할 일 | 완료 기준 |
| --- | --- | --- |
| 월~수 사전 준비 | 투표·주제 문장·문의 범위 합의, 문서 6개·사용자 5명·접수 4건 작성, 공통 시험 질문을 주제에 맞게 변경 | 각자 서비스 흐름을 설명하고 자료 초안을 공유할 수 있음. 수업 77~79일차 참여 병행 |
| 공식 1일차 | 강사 주제 확인, 데이터·권한·계약 확정, 정상 문의 한 건을 처음부터 끝까지 연결 | 근거 있는 답변 1건과 시험 입력·기대 결과 준비 |
| 공식 2일차 | 이관·권한·주입·중복·외부 장애 처리 연결, RAG 비교·통합 시험 | 정상뿐 아니라 실패 상황에서도 정해진 응답이 나옴 |
| 공식 3일차 | 실패 수정·재시험, 변경 마감, 문서와 실행 결과 맞추기, 발표 리허설 | 설계서·RAG 설계서·실행 결과서와 실행 증거 제출 |

RAG는 **같은 평가 질문 10개로 청킹 방식 2개 이상을 비교**하고 검색 기준을 정합니다. LLM 관련 시험은 3회 반복하고, 실제 측정한 결과만 기록합니다. 데이터 API·LLM 장애는 시험 후 해제합니다. 예상 가능한 실패 처리와 별도로 예기치 않은 오류를 받는 게시된 Error Workflow도 준비합니다.

6명은 선정 후 **흐름 통합 / 지식 문서·RAG / API 연동·안정성 / 보안·QA / 시연·문서**의 작업량과 희망을 비교해 배분합니다. 작업량이 큰 분야에 2명을 배치하고 각 워크플로우의 최종 편집 담당자는 1명으로 정합니다. 이 문서에서는 개인 역할을 확정하지 않습니다.

## 9. 아직 정하지 않은 것은 어떻게 정하나요?

| 미정 항목 | 정하는 방법 | 결정 시점 |
| --- | --- | --- |
| 회사명·주제 최종 선택 | 예시는 가상 설정. 팀 투표 후 목표 한 문장을 합의하고 강사에게 범위·중복 확인 | 선정 직후 / 공식 1일차 승인 |
| 가상 모델의 연결 조건·오류 코드와 안전 안내 범위 | 모델 한 종류의 규칙을 정하고 공개 매뉴얼을 참고하되 직접 작성합니다. 위험 상황의 문구는 팀 검토 후 고정하고 수리 절차는 제외합니다. | 문서 작성 시작 전 |
| 자동 답변·이관·긴급 기준 | 각 문의에 정상·애매함·위험 사례를 하나씩 써서 규칙과 기대 결과 합의 | 시험 작성 전 |
| 문서·사용자·접수 담당자 | 희망 역할과 준비량으로 배분하고, 작성자 외 1명이 검토 | 사전 준비 시작 시 |
| 입력 화면·실제 연동 | 기본은 요청 도구+제공 API. 별도 화면·상용 연동은 필수 시험을 해칠지 보고 선택 | 정상 흐름 구현 후 |
| 벡터 저장소·검색 기준·응답 기한 | 지정 환경에서 청킹·검색·지연 시험 후 결정. 메모리 저장소라면 재색인·복구 절차 확인 | 공식 1~2일차 |

## 10. 투표할 때 볼 점

- **좋은 점:** 소비자 입장에서 증상과 수리 접수를 이해하기 쉽고, 일반 안내와 긴급 이관의 차이가 뚜렷합니다.
- **준비 부담:** 제품마다 점검 절차가 다릅니다. 여러 제조사 절차를 섞지 않고 가상 모델 한 종류의 문서를 일관되게 작성해야 합니다.
- **판단 질문:** 내가 사용자의 불편을 설명할 수 있는가? 서로 다른 문의 3개를 말할 수 있는가? 문서 작성·구현·검증 중 맡을 일을 떠올릴 수 있는가?
- **투표 제안:** 5개 중 1순위·2순위와 이유 한 줄, 걱정되는 점 한 줄을 적습니다. 상위 2개를 논의해 최종 후보를 정합니다. 주제 난이도 자체는 가산점이 아닙니다.
